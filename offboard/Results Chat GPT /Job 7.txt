## JOB 7 — KV cache q8_0 and long-range recall

## 1. What do `--cache-type-k` and `--cache-type-v` do? What does q8_0 mean?

### QUOTED

`llama.cpp` documentation lists:

> "`--cache-type-k TYPE` — KV cache data type for K"
> "`--cache-type-v TYPE` — KV cache data type for V"
> "allowed values are ... q8_0 ..."
> "(default: f16)"
> ([Android Git Repositories][1])

Therefore:

* `--cache-type-k q8_0` sets the Key cache storage type to q8_0.
* `--cache-type-v q8_0` sets the Value cache storage type to q8_0.
* If neither flag is supplied, the documented default is `f16`.
  ([Android Git Repositories][1])

### q8_0 meaning

**QUOTED**

A llama.cpp discussion describes q8_0 KV cache as reducing memory:

> "In KV Q8_0, expect a similar PPL as FP16, with a <0.1% PPL bump"
> ([Reddit][2])

# 2. Published measurements of q8_0 KV accuracy cost

## Measurement 1 — Qwen2.5-Coder-7B

### QUOTED

A llama.cpp discussion reports:

| Cache     |         Mean PPL |
| --------- | ---------------: |
| f16/f16   | 8.3891 ± 0.02016 |
| q8_0/q8_0 | 8.3934 ± 0.02017 |

Difference:

* ΔPPL = 0.0043

Source reports the test used:

* `llama-perplexity`
* Qwen2.5-Coder-7B
* q6_k model
* 128k GGUF
  ([GitHub][3])

This is a perplexity measurement, not exact recall.

# Measurement that would prove the distance claim wrong

Claim being tested:

> Long-range recall is degraded more than nearby recall by q8_0 KV quantisation.

A measurement that would disprove it:

* Same model.
* Same prompt.
* Same generation settings.
* Compare f16 KV vs q8_0 KV.
* Place identical known strings at different distances from the generation point.
* Measure exact-match retrieval accuracy.
* If q8_0 has the same retrieval accuracy at early and late positions as f16, the distance-dependent degradation claim is disproven.
